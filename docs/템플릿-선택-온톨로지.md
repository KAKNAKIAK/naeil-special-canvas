# 내일스패셜 템플릿 선택 온톨로지

문서 버전: 1.0 / 확인일: 2026-11-26 / 대상: 상품정보를 읽어 Canvas 프로젝트를 만드는 AI 에이전트.

이 문서는 **상품의 의미 → 전달 목적 → 시작 템플릿 → 블록 → 필드 → 검수**를 연결한다. 별도 실행 엔진이나 앱 입력 스키마가 아니다. 아래 분석용 개념은 AI의 계획에 사용하고, 앱에는 현재 계약에서 지원하는 필드만 전달한다.

## 1. 먼저 읽을 계약과 적용 범위

- 시작 템플릿 실체: `src/catalog.ts`의 `TEMPLATE_PRESETS`, `createTemplateProject`.
- 프로젝트 JSON: `schema/project.schema.json` (현재 2.1.0).
- 생성 가능 블록·개수: `schema/block-catalog.json` (현재 1.0.0).
- 항목 문자열: `src/preset-item-format.ts`, 화면 해석: `src/components/CanvasSection.tsx`.
- CLI: `desktop/cli.cjs`, `src/cli-commands.ts`, `src/App.tsx`의 `editorActions`.

확인 시점 소스에는 CLI 작업 중 변경이 있다. 이 문서는 소스 기준 사용법이며, 설치본·릴리스에 해당 기능이 들어 있다는 보증이 아니다. 실행 중 앱의 `status`가 실제 호출 가능 여부의 최종 기준이다.

시작 템플릿은 완성 상품이 아닌 **예시 데이터가 든 뼈대**다. 예시 도시·날짜·숙박일·상금·마사지 시간·NO쇼핑·포함 혜택·샘플 이미지는 상품 근거로 재사용하지 않는다. 전부 실제 입력과 대조하여 교체하거나 제거한다.

현재 새 프로젝트·샘플·시작 템플릿은 기본 이미지 자산과 연결 없이 생성된다. 필요한 사진은 상품 자료에서 확보한 뒤 추가한다. 이미지가 준비되지 않은 상태에서는 빈 이미지 칸을 유지하고 연결 누락을 검수 항목으로 남긴다.

## 2. 개념과 관계

| 개념 | 뜻 / AI가 추출할 값 | 관계 |
|---|---|---|
| Product | 상품명, 지역, 실제 판매 분류, 여행 기간 | 대상 고객을 가지며 여러 제공 항목을 포함 |
| Audience | 가족, 커플, 골퍼 등 명시된 고객 | 전달 목적을 보조하며 템플릿을 단독 결정하지 않음 |
| Offering | 호텔, 객실, 식사, 투어, 이동, 서비스, 행사 | 조건과 근거를 가짐 |
| Benefit | 포함 특전 또는 조건부 혜택 | Offering을 설명; 유료 옵션과 구분 |
| ChoiceGroup | 함께 고를 수 있는 후보와 선택 수 | 후보 목록, 택 N, 적용 일차·인원·추가금 연결 |
| Comparison | 같은 기준으로 설명할 두 대상 | 두 대상 각각의 사실과 비교 기준 연결 |
| Route | 실제 방문 순서가 있는 장소 목록 | 일정과 연결; 나열된 추천지를 동선으로 추정하지 않음 |
| Itinerary | 일차·시간별 실제 활동 | Route보다 세밀한 순서와 조건을 가짐 |
| Event | 대회·행사, 일정, 참가 조건, 시상 규정 | 일정·표·참가 안내와 연결 |
| Condition | 적용 기간, 인원, 객실, 횟수, 추가금, 제외 사항 | 특정 혜택·선택군에 적용; 분리 시 의미가 바뀌면 함께 표시 |
| Evidence | 원문 인용/위치, 출처, 확인 시점 | 판매 문구의 사실을 뒷받침 |
| Asset | 이미지와 실제 대상, 출처·사용 권리 | 특정 Offering 또는 장소를 묘사 |
| Intent | 선택 안내, 비교, 동선 설명, 숙소 소개, 행사 안내 | 템플릿과 블록을 결정 |
| Template / Block | 전체 흐름 / 개별 표현 단위 | 상품 의미를 표현하며 사실을 새로 만들지 않음 |

모든 핵심 사실에 `confirmed`(명시 근거 있음), `unknown`(없음), `conflicting`(상충)을 구분한다. 원문을 사실로 추출했다는 것과 현재 판매 조건이 검증됐다는 것은 다르다. 날짜·적용 범위도 함께 확인한다.

포함 관계는 `included`, `choose_n`, `paid_optional`, `conditional`, `excluded`, `unknown`으로 분석한다. 이 값들은 분석용 용어이며 새 앱 필드가 아니다. unknown을 included로 바꾸지 않는다.

## 3. 템플릿 선택 순서

### 상품 문서에서 CLI까지의 작업 흐름

상품 문서 → 근거별 사실 추출 → 전달 목적 결정 → 템플릿과 블록 선택 → 상품별 구성 계획 → CLI 상태 조회 → 지원되는 편집 실행 → GUI·HTML 확인 순서로 진행한다.

| 단계 | 입력에서 확인할 내용 | 남길 결과 | 다음 단계에 전달할 값 |
|---|---|---|---|
| 자료 읽기 | 문서명·페이지·표·문단, 적용 기간, 실제 상품 조건 | 사실별 출처와 확인 상태 | fact ID, 원문 위치, 적용 조건 |
| 테마 판별 | 대상 고객, 여행의 중심 경험, 실제 선택·비교·동선·행사 관계 | 주요 전달 목적 1개와 보조 목적 | intent, audience, 관계 |
| 구조 선택 | 템플릿 필수 정보 충족 여부, 실제 이미지 확보 여부 | 프리셋 ID 또는 빈 구성, 블록 순서와 이유 | presetId, section type, 목적 |
| 문구 배치 | 고객이 알아야 할 혜택과 조건, 제목·본문·항목의 역할 | 사실과 연결된 문구·이미지 계획 | factIds, title/body/items, asset ID |
| CLI 작성 | 현재 프로젝트·지원 action·revision | 실행 명령과 실제 반영 결과 | 실제 section ID, 새 revision |
| 검수·전달 | 예시 잔존, 조건 누락, 이미지 대응, 화면 잘림 | 프로젝트 JSON·HTML, 미확인 사항 | 결과 파일과 검수 상태 |

출처가 다른 문서에 같은 혜택이 나오면 하나의 Offering에 근거를 연결한다. 조건이 충돌하면 확정하지 않는다. 원문에 포함된 선택군·적용 인원·횟수·추가금을 고객용 블록까지 함께 전달한다.

이 흐름의 산출물은 해당 상품의 캔버스 초안이다. 시작 템플릿 목록에 새 프리셋을 등록하는 작업에는 별도의 코드 변경이 필요하다. 현재 CLI의 기능별 제약은 8절을 따른다.

### 선택 절차

1. 근거에서 상품·혜택·선택 조건·비교 대상·동선·행사 정보를 추출한다.
2. 가장 중요한 고객 질문을 하나 정한다. “어떤 옵션을 고르나”, “두 상품이 어떻게 다른가”, “어디를 어떤 순서로 가나”, “행사 조건이 무엇인가” 등이다.
3. 아래 필수 조건을 충족하는 템플릿만 후보로 둔다. 허니문이라는 단어만으로 택1, 골프라는 단어만으로 대회 템플릿을 고르지 않는다.
4. 고객 질문에 가장 직접 답하고 예시 삭제·교체가 가장 적은 후보를 고른다. 동률이면 조건 누락 위험이 적은 구성, 더 짧은 구성을 우선한다.
5. 여러 의미가 함께 있으면 주 템플릿은 하나로 두고 필요한 블록만 더한다. 모든 프리셋을 연결하지 않는다.
6. 맞는 후보가 없으면 빈 프로젝트에 블록을 조합한다. 이때 `presetId`는 분석 결과에서 null로 둔다. 존재하지 않는 템플릿 ID를 호출하지 않는다.

## 4. 현재 시작 템플릿 4종

| ID / 기본 분류·layout | 언제 사용 | 필수 정보 | 기본 흐름 | 피해야 하는 경우 / 보정 |
|---|---|---|---|---|
| `theme-multi-city` / 우리만·theme-package | 여러 도시를 하나의 테마와 실제 동선으로 묶어 설명 | 순서가 확인된 방문지 2개 이상, 테마, 실제 특전 | image → route-bar → caption-grid(offer) | 추천 도시 모음만 있으면 동선 생성 금지. 날짜별 상세는 timeline 추가. 특전 4개 예시는 아래 2개 단위 규칙 적용 |
| `honeymoon-pick` / 금까기·hotel-sales | 여러 체험 중 선택하는 구조와 공통 혜택 설명 | 후보 2개 이상, 선택 수·적용 범위, 공통 혜택 구분 | hero-cover → option-grid → caption-grid(offer) | 선택 관계가 없으면 쓰지 않음. 가족·일반 상품에도 의미가 맞으면 사용 가능하나 허니문 문구·분류 교체 |
| `kids-vs` / 우리만·theme-package | 두 여행 방식·프로그램·상품의 차이를 설명 | 정확히 두 대상, 같은 비교 기준, 각각의 실제 내용 | vs-compare → caption-grid → service-bar | 가족이라는 이유만으로 적용 금지. VS는 택1의 증거가 아님. 둘 다 포함이면 그 관계를 본문에 명시. 3개 이상 비교는 table |
| `golf-match` / 골프·golf-standard | 골프 대회·행사 참가 조건과 표 형태 정보 안내 | 실제 행사, 일정·참가 기준; 시상표 사용 시 확정 규정 | hero-cover → list → table → service-bar | 일반 골프 휴양은 제외. 시상 자료 없으면 상금표 제거하고 확인된 일정표로 교체하거나 표 생략 |

프리셋 기본 category와 layout은 예시값이다. category는 실제 판매 분류를 따르고 불명확하면 확인 대상으로 남긴다. layout만 바꿔도 sections가 자동 조립되는 것은 아니다.

## 5. 프리셋 밖 상품의 조합 지침

아래는 **권장 조합**이며 추가 설치된 시작 템플릿이 아니다.

| 상품의 중심 | 권장 layout | 블록 흐름 |
|---|---|---|
| 한 호텔의 객실·시설 설명 | hotel-detail | hero-cover → menu-zigzag → caption-grid → service-bar |
| 호텔 포함 혜택 판매 | hotel-sales | hero-cover → list(offer) → menu-zigzag → text(조건) |
| 여러 지역·여행지 소개 | destination-catalog | text → caption-grid 반복 → service-bar |
| 일차별 상세 여행 | journey-longform | hero-cover → route-bar(순서 확인 시) → timeline → list(주의) |
| 일반 골프 라운딩·숙박 | golf-standard | hero-cover → menu-zigzag(코스) → table(일정) → list(포함/불포함 분리) |
| 기간 한정 혜택 | offer-promotion | hero-cover → list(offer) → text(적용 조건) |
| 하나의 주제 체험 | theme-package | hero-cover → menu-zigzag → service-bar |

자료가 적으면 text와 list만으로 초안을 만든다. 빈 공간을 채우려고 혜택이나 이미지를 창작하지 않는다. 조건·권리 미확인 항목은 내부 검토에 남기며 고객 최종본에는 미확인 판매 주장을 넣지 않는다.

## 6. 생성용 블록 사전

개수는 현재 block-catalog의 생성 계약이다. 화면에서 더 추가 가능하더라도 생성 시 계약을 우선한다. 공통 `title`, `body`를 의미에 맞게 쓰고 중복 카피를 줄인다. 카테고리 라벨 필드는 제거되어 새로 생성하거나 편집하지 않는다.

| type | 전달 의미 / 필요한 정보 | 항목 수·필드 | 선택·주의 기준 |
|---|---|---|---|
| `text` | 소개, 상세 조건, 주의사항 | items 없음; title/body | 사진 없는 설명. 중요 조건을 note에만 숨기지 않음 |
| `image` | 대표 사진, 자유 이미지 배치 | layoutBoxes, mediaIds | 실제 이미지와 레이아웃 필요; 부족하면 text로 대체 |
| `list` | 포함·불포함·주의·특전 나열 | items 1–12; listStyle=list/offer | offer는 강조 모양일 뿐 무료·포함을 뜻하지 않음 |
| `icon-card` | 짧은 장점·시설 요약 | iconCards 1–6 | 각 카드 icon/title/body/tone; 아이콘이 사실을 대신하지 않음 |
| `table` | 동일 열 기준 일정·조건·시상 | tableHeaders/tableRows, 1–20행 | 현재 편집 최대 5열. 모든 행의 열 수 일치; 큰 표는 의미별 분할 |
| `timeline` | 시간·일차 순서 | items 1–30, timelineDayStarts, mediaIds | `시간 | 제목 | 설명`; 대표 이미지 뒤 항목별 이미지. 일차 시작 인덱스 명시 |
| `menu-zigzag` | 호텔·시설·코스별 사진과 상세 | items 1–12, 항목별 mediaIds | `제목 | 설명`; 비교 관계를 암시하지 않는 순차 소개 |
| `caption-grid` | 두 사진·혜택의 병렬 소개 | items 정확히 2, 항목별 mediaIds | `제목 | 설명`; listStyle=offer면 번호 강조. 4개면 2개씩 두 블록 |
| `hero-cover` | 상품 첫인상과 핵심 요약 | 대표 이미지 1, 배지 items 0–6 | 배지에도 근거 필요. 미확인 NO쇼핑·성급·숙박일 자동 생성 금지 |
| `route-bar` | 방문 순서 요약 | 장소 items 2–12, 지도 이미지 선택 | 지도는 선택 사항. 이동수단·소요시간은 자료 있을 때만 본문에 |
| `option-grid` | 선택 후보 안내 | items 2–12, 후보별 이미지 | items는 후보명. title/body에 택 N, 적용 일차·대상·추가금 명시 |
| `vs-compare` | 정확히 두 대상의 비교 | items 정확히 2, 이미지 2 | `태그 | 제목 | 설명`; 같은 기준 사용. 3번째 항목은 화면에 표시되지 않음 |
| `service-bar` | 서비스와 핵심 키워드 | items 1–12 | `서비스 설명 | 강조 키워드`; 상세 취소규정·복잡한 요금표에는 부적합 |

`offer` type은 legacy이며 신규 생성 금지. `list` + `listStyle: "offer"`로 표현한다.

문자열의 `|`는 구조 구분자다. 제목·태그 안에는 넣지 말고 필요하면 `·`로 바꾼다. 이미지 배열은 항목 순서와 대응시키고, 실제 존재하는 asset ID만 참조한다. 사진 없는 항목 때문에 뒤 사진을 앞으로 당겨 연결하지 않는다.

### 현재 구현과 계약의 차이

- theme-multi-city 기본 caption-grid는 4개 항목인데 계약은 2개다. AI 출력은 두 블록으로 나눠 계약을 지킨다. 이번 문서는 소스 프리셋을 수정하지 않는다.
- route-bar 카탈로그는 이미지 슬롯 1개를 기술하지만 화면은 선택 지도 슬롯이다. 지도 없음을 이동 경로 오류로 해석하지 않는다.
- CLI section.update는 모든 Section 필드를 받지 않는다. iconCards, timelineDayStarts, layoutBoxes 등을 무작정 패치하지 말고 다음 절의 지원 범위를 확인한다.

## 7. AI 분석 결과 형식 — 앱 입력과 별도

AI는 먼저 다음 구조의 계획을 만든다. ID와 revision은 예시에서 복사하지 말고 실제 조회로 얻는다.

```json
{
  "ontologyVersion": "1.0",
  "intent": "선택 안내",
  "presetId": "honeymoon-pick",
  "reason": "확인된 후보 중 1개 선택, 공통 특전은 별도 포함",
  "facts": [
    {"id": "f1", "value": "체험 A 또는 B 중 1개 선택", "relation": "choose_n", "source": "사용자 제공 상품 원문 2문단", "status": "confirmed"}
  ],
  "sections": [
    {"type": "option-grid", "purpose": "후보 선택", "factIds": ["f1"], "conditions": ["전체 일정 중 1회"]}
  ],
  "needsReview": ["선택 프로그램의 추가금 유무"],
  "deliveryStage": "internal-draft"
}
```

위 내용은 형식 설명을 위한 가상 예시다. 실제 원문에 전체 일정 중 1회가 없다면 conditions에 넣으면 안 된다. 이 계획 JSON을 project JSON이나 dispatch payload로 직접 넘기지 않는다. 각 고객 노출 문구가 어떤 factIds에서 나왔는지 계획에 남긴다. 근거 없는 숫자·상금·일정·혜택은 보류한다.

## 8. 현재 CLI에 연결하는 방법

프로젝트 루트에서 실행하며 Node와 CLI가 연결된 데스크톱 앱이 필요하다. 일반 브라우저 실행만으로 연결된다고 가정하지 않는다.

```powershell
node desktop/cli.cjs status
node desktop/cli.cjs get
node desktop/cli.cjs dispatch --file command.json
node desktop/cli.cjs dispatch --file export-command.json --out draft.html
```

1. status에서 actions/params/sectionTypes/readOnly를 확인한다. 필요한 기능이 없으면 해당 동작을 중단한다.
2. get으로 현재 프로젝트와 revision을 읽는다. 사용자 작업물을 임의로 빈 템플릿으로 교체하지 않는다. 기존 데이터 백업은 export.json을 파일로 내보낸다.
3. AI 계획을 검토한 후, 현재 프로젝트에서 필요한 변경만 한 명령씩 실행한다. 모든 변경에 최신 expectedRevision을 넣는다.
4. section.add 뒤 get을 다시 호출해 새 ID와 위치를 확인한다. ID를 추측하지 않는다. 필요하면 section.reorder로 순서를 조정한다.
5. section.update로 문구·items·tableHeaders/tableRows·mediaIds 등을 채운다. get으로 실제 반영을 대조한다.
6. qa 결과를 읽고 오류를 해결한다. export.html 또는 export.json으로 산출물을 만든다. GUI와 HTML에서 잘림·이미지 연결·조건 노출을 확인한다.

예: `command.json` (revision 12는 예시이며 실제 최신 값으로 교체):

```json
{"action":"section.add","args":["option-grid"],"expectedRevision":12}
```

예: get에서 ID·revision을 확인한 뒤 실행할 수정 payload:

```json
{"action":"section.update","args":["실제-section-ID",{"title":"체험 프로그램 택 1","body":"원문에서 확인한 선택 조건을 입력","items":["체험 A","체험 B"]}],"expectedRevision":13}
```

예: `export-command.json`:

```json
{"action":"export.html","args":[]}
```

현재 확인한 한계:

- template 적용, 새 프로젝트 생성, 전체 JSON import, 이미지 업로드 전용 action은 현재 editorActions에 없다. `template.apply`, `project.create`, `asset.upload` 같은 명령을 만들어 호출하지 않는다. GUI에서 빈 프로젝트·프리셋·이미지를 준비하거나 별도의 구현 작업이 필요하다.
- CLI는 완전한 무인 생성 파이프라인이 아니다. 기존 GUI 프로젝트의 지원 필드를 편집하는 경로다.
- section.update는 title/body/note, items/mediaIds/tableHeaders/tableRows, mediaLayout/contentLayout/background/listStyle, hidden/timelineHeroVisible만 허용한다. 레이아웃 변경은 지원하는 layout.set도 확인한다.
- icon-card 항목 변경은 item.update를 사용한다. timelineDayStarts·layoutBoxes 등 직접 쓰기가 필요한 구성은 현재 CLI만으로 완료할 수 있다고 보고하지 않는다.
- project.save는 저장 창과 사용자 입력이 필요할 수 있다. 파일 산출은 export.json + --out 경로를 사용할 수 있다.
- 연결된 프로젝트 JSON을 외부에서 수정한 경우 `project.refresh`의 args `[false]`로 다시 읽을 수 있다. `project.autoRefresh`의 args `[true]`는 자동 감지를 켠다. `status.refresh`의 오류·마지막 반영 시각을 확인한다. 미저장 편집 충돌 시 내용을 검토하며, `[true]` 새로고침으로 사용자 편집을 임의 교체하지 않는다. 새 파일의 최초 import는 여전히 GUI에서 수행한다.
- REVISION_CONFLICT면 get 후 계획을 재대조한다. timeout은 변경이 없었다는 뜻이 아니므로 재조회 없이 같은 추가 명령을 재전송하지 않는다.
- 여러 dispatch는 하나의 트랜잭션이 아니다. 일부만 성공하면 완료 지점과 남은 변경을 기록한다. GUI 사용자의 중간 편집을 일괄 undo로 지우지 않는다.
- 연결 파일의 토큰은 읽어서 출력·문서화하지 않는다. CLI가 기존 인증을 처리하게 둔다.
- Getty 공개 미리보기 추가는 `asset.addGetty` args `["실제 콘텐츠 코드"]`를 사용한다. 숫자 또는 영문·숫자 코드를 지원하며 원본 다운로드·사용권 확인은 별도다.

## 9. 선택 예시와 합격 기준

| 입력 상황 | 올바른 판단 | 금지할 판단 |
|---|---|---|
| 허니문, 조식·픽업만 확인 | hotel-sales 조합 + 확인된 혜택 list | 허니문이므로 마사지·택1 체험 추가 |
| 가족 상품, 투어 3개 중 택1 명시 | option-grid, 선택 조건 표시 | kids-vs에 3개 넣기 |
| 가족 대상 두 프로그램, 모두 포함 | kids-vs 가능; 모두 포함을 명시 | VS를 택1이라고 표현 |
| 4개 도시 방문 순서·테마 확인 | theme-multi-city, 혜택은 2개씩 분할 | 이동수단·시음 포함을 예시에서 복사 |
| 골프 호텔 3박·라운딩만 확인 | 일반 골프 조합 | 대회 상금표 생성 |
| 대회 참가·일정 확인, 상금 미정 | golf-match에서 상금표 제거 | 예시 500만원 사용 |
| 호텔 3곳 동일 조건 비교 | table 또는 순차 소개 | vs-compare 세 번째 항목에 넣기 |
| 추천 도시만 있고 이동 순서 없음 | destination-catalog | route-bar로 임의 순서 확정 |

완료 조건:

- 프리셋 4종 중 선택 또는 null의 이유가 설명된다.
- 선택·포함·별도 유료·조건부 관계가 서로 바뀌지 않는다.
- 판매 문구에 근거가 있고, 미확인·상충 정보가 분리된다.
- 예시 상품명·날짜·상금·이미지·혜택이 남지 않는다.
- 13개 생성 블록 계약과 프로젝트 스키마, 이미지 연결이 맞는다.
- CLI는 실행 중 status가 제공하는 기능만 호출하고 최신 revision을 사용한다.
- QA 통과와 시각 검수, 고객 조건 검토를 별개로 기록한다. QA 통과만으로 상품 사실·이미지 권리가 검증됐다고 판단하지 않는다.

## 10. AI에 줄 작업 지시문

> 이 문서와 현재 project.schema.json, block-catalog.json을 읽고 제공 상품정보를 근거별로 정리하라. 먼저 포함/선택/유료/조건부 관계와 고객 질문을 결정하고, 템플릿 선택 이유·블록 순서·미확인 항목을 제시하라. 프리셋 예시는 사실로 사용하지 마라. CLI status/get으로 실제 지원 기능과 현재 프로젝트를 확인한 후 승인된 작업 범위에서 지원되는 변경만 수행하라. 명령마다 revision과 반영 결과를 확인하고, 지원되지 않는 이미지·프로젝트 생성 단계는 미완료로 명시하라. 최종적으로 JSON/HTML, QA 결과와 시각 검수 여부, 미해결 조건을 보고하라.

프리셋·블록·문자열 형식·CLI action이 바뀌면 해당 절과 선택 예시를 함께 갱신한다. 이 저장소의 AGENTS.md는 상품 문서 기반 작성 전에 이 문서를 읽도록 지시한다. 외부 AI에 상품 자료를 전달할 때도 이 문서와 현재 계약을 함께 제공한다. 앱 실행 중 자동 로딩과 설치본 동봉은 현재 구현되어 있지 않다.
