# 내일스패셜 AI 자동작성 Skill 통합 작업계획서

## 한줄 결론

여행상품 정보를 AI와 사용자가 함께 기획하고, 사용자가 구조를 최종 컴펌한 뒤에만 **내일스패셜 캔버스용 로드 JSON을 생성**하는 구조를 만든다. 프리셋과 앱 구조의 변경은 스키마 버전·마이그레이션·호환성 검증으로 흡수하고, 검증된 계약 파일은 앱 빌드·배포 시 Skill 참조 폴더에 자동 동기화한다.

## 1. 프로젝트 목표

현재 PPT·Excel·수작업 중심의 기획안 제작을 다음 흐름으로 전환한다.

```text
여행상품 자료 입력
→ 사실과 기획 문구 분리
→ AI가 콘텐츠 구조·블록 순서 초안 제안
→ 사용자와 구조·강조점·이미지 방향 협의
→ 사용자 최종 컴펌
→ 캔버스 로드용 JSON 생성
→ 앱에서 자동 조립
→ 담당자가 문구·이미지·레이아웃 보정
→ 독립 HTML 또는 디자이너 전달 ZIP 출력
```

AI가 앱 화면을 클릭해서 작성하는 방식은 기본 구조로 삼지 않는다. AI는 앱과 동일한 데이터 계약에 맞는 JSON을 만들고, 앱은 이를 불러와 편집·미리보기·내보내기를 담당한다.

## 2. 사용자 이용 시나리오

### 기본 입력

- 상품명 또는 여행지 키워드
- 상품 일정표
- 호텔·관광지·교통 정보
- 상품 특전과 포함·불포함 사항
- 가격과 판매 기간
- 사용자가 제공한 이미지 또는 이미지 URL
- 기존 상품 페이지나 내부 자료

### 기대 결과

사용자가 “괌 두짓타니 4박 5일 가족여행 상품으로 내일스패셜 만들어줘”라고 요청하면 AI는 곧바로 JSON을 만들지 않고 다음 순서로 진행한다.

1. 입력 자료를 사실 정보, 기획 문구, 확인 필요 항목으로 나눈다.
2. 상품의 핵심 고객과 메시지를 정한다.
3. 필요한 블록, 순서, 각 블록의 역할을 초안으로 제안한다.
4. 공통 텍스트의 톤, 강조할 특전, 일정의 상세 수준, 이미지 역할을 사용자와 함께 조정한다.
5. 사용자가 구조를 최종 컴펌하면 그 컴펌본을 `approved brief`로 저장한다.
6. 승인된 brief를 기준으로만 공통 텍스트·블록별 항목·이미지 슬롯을 작성한다.
7. 앱에서 열 수 있는 로드용 JSON을 생성하고 유효성, 누락 이미지, 미확인 사실을 검수한다.

## 3. 목표 시스템 구조

| 영역 | 역할 | 주요 산출물 |
|---|---|---|
| 입력 수집 | 사용자 자료, URL, 문서, 이미지 수집 | 원본 자료 목록 |
| 사실 정리 | 사실·추정·기획 문구 분리 | fact pack, 확인 필요 목록 |
| 공동 기획 | 상품 메시지, 블록 종류와 순서 초안 제안 및 사용자 조정 | approved brief |
| 자동작성 Skill | 승인된 brief만 앱 구조에 맞는 데이터로 변환 | 로드용 Project JSON |
| 계약 검증 | 스키마·블록·이미지 연결 검사 | validation report |
| 캔버스 앱 | JSON 불러오기, 사람 편집, 미리보기 | 수정된 프로젝트 |
| 내보내기 | HTML과 이미지 패키징 | 독립 HTML, JSON, 디자이너 ZIP |

## 4. 앱과 Skill의 역할 분리

### 앱이 책임질 것

- 프로젝트 JSON 저장과 불러오기
- 블록 렌더링과 사용자 편집
- 프리셋 기본값과 화면 레이아웃
- 이전 JSON을 현재 버전으로 변환
- HTML·ZIP 내보내기
- 현재 지원 기능을 기계가 읽을 수 있는 형태로 제공

### 자동작성 Skill이 책임질 것

- 여행상품 자료 해석과 구조화
- 블록 선택과 순서의 **초안 제안**
- 컴펌 전에는 구조와 문구 방향만 제안하고 로드 JSON을 생성하지 않음
- 승인된 brief를 기준으로 제목·본문·항목·일정 문구 작성
- 승인된 이미지 방향을 기준으로 역할과 슬롯 배정
- 앱이 지원하는 최신 계약 확인
- 로드용 JSON 생성과 사전 검증

### 사람이 반드시 확인할 것

- 가격, 판매 기간, 항공편, 호텔 등급, 포함 조건
- 이미지의 실제 대상 일치 여부
- 이미지 사용 권리와 최종 사용 승인
- 과장 표현과 사실 오류
- 최종 디자인 완성도

## 5. 자동작성 Skill 설계안

권장 Skill 이름은 `naeil-special-canvas-writer`다. 기존 `naeil-special-planner`는 조사·기획 자료를 만들고, 신규 Skill은 이를 캔버스 Project JSON으로 변환한다. `naeil-special-html`은 기존 manifest 기반 HTML 제작이 필요한 업무에 계속 사용한다.

```text
naeil-special-canvas-writer/
├── SKILL.md
├── agents/
│   └── openai.yaml
├── scripts/
│   ├── build_project.py
│   ├── validate_project.py
│   └── migrate_project.py
├── references/
│   ├── canvas-contract/
│   │   ├── project.schema.json
│   │   ├── schema-version.json
│   │   ├── block-catalog.json
│   │   └── contract-manifest.json
│   ├── content-routing.md
│   ├── approved-brief.schema.json
│   └── compatibility-policy.md
└── assets/
    └── project-template.json
```

`references/canvas-contract/`는 Skill에서 직접 편집하지 않는다. 앱 저장소의 공식 계약을 빌드·배포 과정에서 자동 동기화한 읽기 전용 사본으로 취급한다.

### Skill 실행 순서

1. 동기화된 `contract-manifest.json`, `schema-version.json`, `block-catalog.json`을 읽고 계약 해시를 확인한다.
2. 입력 자료를 fact, copy, media 후보로 나눈다.
3. 상품 유형에 맞는 블록 구성 초안을 제안한다.
4. 사용자와 확정한 `approved brief`가 있는지 확인한다.
5. 컴펌 전이면 JSON 대신 기획안과 결정이 필요한 항목만 반환한다.
6. 컴펌 후에만 Project JSON을 생성하고 결정형 검증 스크립트를 실행한다.
7. 형식·기본값처럼 결정적으로 고칠 수 있는 오류만 자동 수정한다. 사실·가격·이미지 대응처럼 판단이 필요한 오류는 임의 수정하지 않고 사용자 검토 목록으로 남긴다.
8. 검증을 통과한 JSON과 요약 보고서를 전달한다.

### approved brief 규격

컴펌 여부를 대화 문맥에만 의존하지 않고 구조화된 파일로 남긴다.

```json
{
  "status": "approved",
  "approvedAt": "2026-07-22T00:00:00+09:00",
  "message": "상품의 핵심 메시지",
  "audience": "핵심 고객",
  "blockOrder": ["text", "image", "list"],
  "confirmedFacts": [],
  "needsReview": [],
  "imageDirections": []
}
```

- `status`가 `approved`가 아니면 로드 JSON을 생성하지 않는다.
- 승인 후 사실이나 블록 순서가 바뀌면 brief를 다시 승인한다.
- 원본 자료 전체를 Project JSON에 복제하지 않고, 생성에 필요한 근거와 확인 상태만 기록한다.

## 6. 현재 블록 라우팅 기준

| 정보 특성 | 사용할 블록 |
|---|---|
| 핵심 메시지와 설명 | 텍스트 |
| 사진 중심 소개, 텍스트·이미지 반복 | 이미지 |
| 장점, 체크포인트, 특전 | 목록 |
| 아이콘으로 구분되는 선택 이유 | 아이콘 카드 |
| 날짜별 핵심 일정 요약 | 간략 일정표 |
| 시간·설명·이미지가 필요한 일정 | 상세 일정표 |
| 객실·식당·관광지처럼 이미지와 설명을 짝지은 소개 | 이미지·설명 카드 |

AI는 모든 블록을 채우려고 하지 않는다. 입력 정보와 상품 목적에 필요한 블록만 사용하고, 같은 내용을 여러 블록에 반복하지 않는다.

신규 자동작성에서 선택 가능한 블록은 위 7개로 제한한다. 현재 앱이 저장본 호환을 위해 유지하는 `offer`, `caption-grid`는 계약 카탈로그에 `legacy: true`, `generatable: false`로 등록하고 Skill은 새로 생성하지 않는다.

### 6.1 콘텐츠 기반 구성 전략

카테고리는 상품의 성격을 보조하는 정보로만 사용한다. 자동작성의 블록 순서는 카테고리별 고정 배열이 아니라, 입력 자료에서 아래 신호를 분석해 결정한다.

| 구성 전략 | 판단 신호 | 기본 블록 흐름 |
|---|---|---|
| 사진 중심 | 이미지 3장 이상, 객실·풍경·시설 등 시각 소개 정보가 많음 | 이미지 → 이미지·설명 카드 |
| 상세 일정 | 시간 표기 2건 이상 또는 일정 줄 4건 이상 | 텍스트 → 상세 일정표 → 이미지 |
| 특전·장점 중심 | 특전·포함·혜택·확정 정보가 많음 | 텍스트 → 아이콘 카드 → 목록 |
| 간략 일정 | 날짜·일차 중심의 일정 정보가 있음 | 텍스트 → 간략 일정표 → 이미지·설명 카드 |
| 스토리형 | 사진과 장소·경험 설명이 함께 있음 | 텍스트 → 이미지 → 이미지·설명 카드 |
| 최소 구성 | 확인된 자료가 적음 | 텍스트 → 이미지 → 목록 |

- 같은 입력은 같은 결과가 나오도록 결정 과정을 고정하되, 서로 다른 자료가 같은 블록 순서로 수렴하지 않게 한다.
- 사용자가 방향을 명시하면 `compositionHint`로 자동 판단을 덮어쓸 수 있다.
- draft brief에는 선택한 `composition.strategy`와 선택 사유(`composition.reason`)를 기록해 검토자가 생성 근거를 확인할 수 있게 한다.
- 최종 문구는 확인된 사실만 사용하고, 짧고 담백하게 작성한다. 추상적 감탄사나 근거 없는 과장 표현은 생성하지 않는다.

## 7. 구조 변경에 대한 핵심 안전장치

프리셋 추가와 앱 구조 변경을 막을 필요는 없다. 대신 변경을 흡수하는 아래 계약 계층을 먼저 만든다.

### 7.1 스키마 버전 분리

프로젝트 JSON에 다음 버전을 명시한다.

```json
{
  "schemaVersion": "2.1.0",
  "catalogVersion": "1.0.0",
  "generator": {
    "name": "naeil-special-canvas-writer",
    "version": "1.0.0"
  }
}
```

- `schemaVersion`: 데이터 필드와 구조의 버전
- `catalogVersion`: 지원 블록과 프리셋 정의의 버전
- `generator.version`: JSON을 만든 Skill 버전

화면 문구나 아이콘 변경은 스키마 버전을 올리지 않는다. 필드 추가처럼 하위 호환이 가능한 변경은 minor, 필드 삭제·의미 변경은 major로 관리한다.

현재 앱의 `schemaVersion: "2.0"`은 정식 SemVer 도입 전 값으로 간주한다. `2.0`과 무버전 JSON은 순차 migration으로 현재 `2.1.0`까지 정규화한다.

### 7.2 블록 ID와 화면 이름 분리

`timeline` 같은 블록 타입 ID는 한 번 배포하면 의미를 바꾸지 않는다. 화면의 `상세 일정표`라는 이름은 자유롭게 바꿀 수 있지만 저장 데이터의 ID는 유지한다.

새 프리셋이 기존 블록의 표현만 바꾸는 경우에는 새 블록 타입을 만들지 않고 `variant`를 추가한다.

```json
{
  "type": "list",
  "variant": "offer"
}
```

### 7.3 앱이 제공하는 블록 카탈로그

Skill 문서에 블록 구조를 하드코딩하지 않는다. 앱 저장소에 `block-catalog.json`을 두고 다음 정보를 관리한다.

- 지원 블록 타입과 variant
- 필수·선택 필드
- 기본값
- 최소·최대 항목 수
- 이미지 슬롯 규칙
- 허용 레이아웃
- 폐기 예정 필드와 대체 필드
- 신규 생성 가능 여부와 legacy 여부

Skill은 실행할 때 이 파일을 읽어 현재 앱이 지원하는 구조만 생성한다.

### 7.4 순차 마이그레이션

앱은 예전 JSON을 바로 현재 구조로 해석하지 않고 버전별 변환을 순서대로 실행한다.

```text
2.0.0 JSON
→ migrate 2.0.0 to 2.1.0
→ migrate 2.1.0 to 2.2.0
→ 현재 앱에서 편집
```

- 원본 JSON은 수정하지 않는다.
- 마이그레이션 전 자동 백업을 만든다.
- 변환 로그를 프로젝트에 남긴다.
- 변환 후 저장할 때만 최신 버전으로 저장한다.
- `schemaVersion`이 없거나 `2.0`인 기존 로드 JSON도 첫 migration의 입력으로 인정한다.

### 7.5 미지원 블록의 안전한 처리

알 수 없는 블록을 임의로 텍스트 블록으로 바꾸면 데이터가 사라질 수 있다. 다음 정책으로 바꾼다.

- 미지원 블록은 원본 데이터를 그대로 보존한다.
- 캔버스에는 `현재 버전에서 지원하지 않는 블록` 자리표시자를 보여준다.
- 사용자가 삭제하거나 마이그레이션하기 전까지 저장 시에도 원본을 유지한다.
- Skill은 앱 카탈로그에 없는 블록을 생성하지 않는다.

### 7.6 왕복 무손실 테스트

다음 검사를 자동화한다.

```text
JSON 불러오기 → 앱 정규화 → JSON 다시 저장
```

사용자가 수정하지 않은 필드와 미지원 확장 데이터가 사라지지 않아야 한다. 이 검사를 `round-trip test`로 고정한다.

현재 정규화 함수가 기본값을 강제로 덮어쓰는 필드도 회귀 대상으로 포함한다. 루트·블록·이미지 객체에서 앱이 모르는 확장 필드는 `extensions` 또는 원본 보존 영역을 통해 다시 저장할 때 유지한다.

### 7.7 이전 버전 회귀 테스트

최소한 아래 fixture를 유지한다.

- 현재 버전의 모든 블록을 포함한 프로젝트
- 직전 버전 프로젝트
- 2개 이상 이전 버전 프로젝트
- 새 필드가 없는 최소 프로젝트
- 앱이 모르는 미래 블록을 포함한 프로젝트
- 이미지 URL과 로컬 이미지가 함께 있는 프로젝트

프리셋이나 앱 구조를 수정할 때 이 fixture가 모두 열리고 다시 저장되는지 확인한다.

### 7.8 앱 업데이트 시 사용자·앱·Skill의 책임

앱 업데이트 후 사용자가 JSON을 직접 수정하거나 Skill을 다시 설치하지 않아도 되게 한다. 호환성 처리의 책임은 앱과 배포 과정에 둔다.

```text
앱 업데이트
→ 새 schema·catalog을 앱과 함께 배포
→ 사용자가 기존 프로젝트를 열기
→ 앱이 schemaVersion을 확인
→ 필요 시 순차 migration 실행
→ 원본 백업과 변환 로그 저장
→ 변환본을 열어 사용자가 결과만 확인
```

| 주체 | 업데이트 후 책임 | 사용자가 해야 할 일 |
|---|---|---|
| 캔버스 앱 | 버전 감지, 순차 마이그레이션, 원본 백업, 변환 로그, 미지원 블록 보존, 변환 결과 안내 | 기존 프로젝트를 열고 결과만 확인 |
| 자동작성 Skill | 실행 시 최신 `schema-version.json`과 `block-catalog.json`을 읽고, 새 프로젝트 JSON만 현재 계약에 맞게 생성·검증 | 별도 설치·수정 없음 |
| 사용자 | 변환 결과와 자리표시자, 사실 확인 목록을 검토 | 이상이 없으면 계속 편집 |

- 기존 블록의 의미가 바뀌거나 필드를 삭제하는 major 변경은 자동 저장 전에 `안전 변환 후 열기 / 원본 그대로 열기 / 취소` 선택지를 보여준다.
- 앱이 모르는 블록은 자리표시자로 표시하되 원본 데이터는 그대로 저장한다.
- Skill은 기존 프로젝트를 마이그레이션하거나 사용자의 JSON을 덮어쓰지 않는다. 이 기능은 앱의 `src/migrations/`가 단일 책임으로 가진다.
- 사용자에게는 `이 프로젝트는 이전 버전입니다. 최신 형식으로 안전하게 변환했습니다.`와 같이 결과 중심으로만 안내한다.

### 7.9 계약 파일 갱신의 소유권과 배포 게이트

`project.schema.json`, `schema-version.json`, `block-catalog.json`은 Skill 문서가 아니라 **앱 구조의 공식 산출물**이다. 공식 원본은 앱 저장소의 `schema/` 한 곳에만 두고, Skill은 자동 동기화된 사본만 읽는다.

```text
naeil-special-canvas/schema/                 ← 유일한 원본
├── project.schema.json
├── schema-version.json
├── block-catalog.json
└── contract-manifest.json

.agents/skills/naeil-special-canvas-writer/
└── references/canvas-contract/              ← 자동 배포 사본
```

`contract-manifest.json`에는 최소한 다음 정보를 기록한다.

```json
{
  "canvasAppVersion": "1.0.0",
  "schemaVersion": "2.1.0",
  "catalogVersion": "1.0.0",
  "contractHash": "SHA-256",
  "syncedAt": "2026-07-22T00:00:00+09:00"
}
```

계약 내용 자체를 코드에서 추측해 자동 작성하지는 않는다. 대신 구조 변경 감지기가 계약 갱신 누락을 빌드 오류로 막고, 검증된 공식 계약을 Skill 참조 폴더에 복사하는 과정만 자동화한다.

```text
앱 타입·블록·프리셋 변경
→ schema / catalog 수정
→ 하위 호환 여부 판단 및 schemaVersion 결정
→ 필요 시 migration 추가
→ 앱 UI·기본값 수정
→ fixture / round-trip / validator 검사
→ contract-manifest와 SHA-256 생성
→ Skill references/canvas-contract에 원자적 동기화
→ Skill이 동기화된 계약으로 생성 가능한지 검사
→ 앱과 계약 파일을 함께 배포
```

자동 동기화는 `npm run contract:sync`로 제공하고 `prebuild`, EXE 빌드 배치, 배포 검사에서 공통 호출한다. `npm run contract:check`는 앱 타입·블록 정의와 계약의 불일치, 원본과 Skill 사본의 해시 불일치를 검사한다.

동기화 도중 일부 파일만 바뀌지 않도록 임시 폴더에 전체 계약을 복사·검증한 뒤 대상 폴더를 교체한다. Skill 폴더가 없거나 쓰기 불가능하면 앱 배포를 성공 처리하지 않고 원인을 명확히 알린다.

배포 또는 CI에서는 최소한 다음을 실패 조건으로 둔다.

- 저장 구조나 블록 정의가 바뀌었는데 계약 파일이 갱신되지 않은 경우
- major 또는 비호환 변경인데 migration이 없는 경우
- 이전 fixture가 열리지 않거나 round-trip 후 데이터가 사라지는 경우
- 앱 카탈로그에 없는 블록을 Skill이 생성하는 경우
- 앱 원본 계약과 Skill 배포 사본의 `contractHash`가 다른 경우
- 앱 버전·스키마 버전·카탈로그 버전 조합이 manifest와 다른 경우

Skill 실행 시 manifest 해시가 맞지 않거나 지원하지 않는 schema major 버전이면 JSON 생성을 중단하고 `계약 동기화 필요`를 반환한다. Skill 내부에는 블록 구조를 별도로 하드코딩하지 않는다.

## 8. 프리셋 추가·수정 표준 절차

프리셋 변경은 다음 순서를 따른다.

1. 기존 블록의 variant인지 새로운 데이터 구조인지 판단한다.
2. 블록 카탈로그와 JSON Schema를 먼저 수정한다.
3. 앱 기본값과 편집 UI를 수정한다.
4. 필요한 경우 마이그레이션 함수를 추가한다.
5. Skill의 블록 선택 규칙을 갱신한다.
6. 기존·신규 fixture와 round-trip 테스트를 실행한다.
7. 로드 JSON, 미리보기, 독립 HTML, 디자이너 ZIP을 모두 확인한다.

개발자 인수 기준: 위 변경 묶음이 완료되지 않은 프리셋·블록 변경은 앱 업데이트로 배포하지 않는다. 계약 파일, 마이그레이션, fixture 검증 결과를 함께 남긴다.

블록을 삭제할 때는 최소 두 버전 동안 deprecated 상태로 유지한다. 기존 타입 ID를 다른 용도로 재사용하지 않는다.

## 9. 입력과 출력 보안

구조 호환성과 별개로 외부 자료를 다루는 안전장치도 필요하다.

- JSON 불러오기 용량과 이미지 개수를 제한한다.
- HTML에 삽입되는 텍스트와 속성값을 정리하고 스크립트를 제거한다.
- 이미지 URL은 `http`와 `https`만 허용한다.
- URL 이미지의 파일 크기, MIME 타입, 다운로드 시간 제한을 둔다.
- ZIP 내부 파일명은 안전한 상대 경로로 변환해 경로 이동을 차단한다.
- 이미지마다 원본 URL·원본 파일명·패키지 경로·변환 형식·다운로드 상태·실패 사유를 기록한다.
- 다운로드 실패 이미지는 성공한 것처럼 처리하지 않고 placeholder와 `needsReview` 항목으로 남긴다.
- AI가 만든 가격·일정·포함 조건은 근거가 없으면 확정값으로 표시하지 않는다.
- 자동 생성본은 기본적으로 `internal-draft`로 만들고, 사람 승인 없이 `customer-final`로 바꾸지 않는다.

## 12. 완료 정의

다음 조건을 모두 만족하면 1차 프로젝트를 완료한 것으로 본다.

- 사용자가 여행상품 자료를 주면 Skill이 앱 로드용 JSON을 생성한다.
- JSON을 불러오면 블록, 텍스트, 항목, 이미지 연결이 정상적으로 나타난다.
- 기존 버전 JSON도 데이터 손실 없이 열린다.
- 앱에 프리셋을 추가해도 Skill 전체를 다시 작성할 필요가 없다.
- 앱 빌드·배포 시 공식 계약과 Skill 참조 사본이 자동 동기화되고 해시가 일치한다.
- 계약 버전이 맞지 않으면 Skill이 JSON 생성을 중단하고 동기화 필요 상태를 알린다.
- 자동 생성 결과에서 확인이 필요한 사실이 분리되어 표시된다.
- 디자이너 ZIP을 풀면 HTML과 모든 다운로드 가능 이미지가 함께 열린다.
- 사용자가 앱에서 수정한 결과를 다시 JSON으로 저장하고 재로드할 수 있다.

## 13. 첫 실행 작업

첫 개발 작업은 Skill 작성이 아니라 아래 계약·검증 기반을 만드는 것이다.

1. `schema/project.schema.json`
2. `schema/schema-version.json`
3. `schema/block-catalog.json`
4. `schema/contract-manifest.json`
5. `src/migrations/`와 이전 버전 fixture
6. `contract:check`, `contract:sync`와 prebuild 연결

이 기반이 완성된 뒤 `naeil-special-canvas-writer`를 만든다. 이후 앱을 업데이트할 때마다 계약 검증과 Skill 참조 사본 동기화가 자동 실행되어야 빌드·배포가 완료된다.

## 14. 구현 완료된 3단계 작성 흐름

### 1단계 — 자료 입력

- 앱 상단 `AI 작성`에서 상품명·카테고리·여행지·레이아웃, 원본 상품 자료, 자료 URL, 사실 확인 상태, 사용할 이미지를 입력한다.
- 원본 텍스트·URL·사실 상태는 프로젝트의 로컬 `briefWorkspace`에 보존한다.
- 일반 로드 JSON과 디자이너 ZIP에는 원본 자료를 넣지 않는다. 필요할 때만 brief JSON을 별도로 저장한다.

### 2단계 — draft brief 검토

- 입력 자료를 바탕으로 블록 순서·공통 문구·확인 완료 사실·확인 필요 항목·이미지 역할을 `draft brief`로 구조화한다.
- 앱과 `naeil-special-canvas-writer/scripts/build_draft_brief.py`는 같은 원칙으로 초안을 만들며, 초안 상태에서는 Project JSON을 생성하지 않는다.
- 사용자는 공통 텍스트, 블록 순서·제목·본문을 조정할 수 있다. 입력 변경 또는 brief 수정은 승인을 자동 해제한다.

### 3단계 — 승인·캔버스 반영

- 사용자가 `이 구조 승인` 또는 `최종 승인`을 누르면 `status: approved`와 승인 시각을 기록한다.
- 승인 brief만 현재 계약의 `internal-draft` Project JSON으로 변환해 기존 캔버스에 반영한다.
- `needsReview`는 Project extensions에 남아 가격·일정·포함 조건을 자동 확정하지 않는다.

### 검증 기준
